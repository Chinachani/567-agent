# 云端跟进 1.3.x 补丁

本轮云端执行器可通过 GitHub connector 提交并更新分支，但不必持有用户本机的 Git 凭据，也不必直接拥有打标签工具。

仅在本轮发布出现必须修改源码的问题时，修复并检查后提交到 main，同时更新桌面/Android版本、Android版本码和新版本发布说明。版本必须为尚未发布的 1.3.x 补丁，Android版本码为 `10300 + patch`。保留原标签及正式发布。

拿到最终代码提交的完整SHA后，再通过 GitHub connector 单独提交 `.github/cloud-release-request.json`：`enabled` 设为 `true`，`version` 为新补丁版本，`sha` 为已经包含在 main 中的该代码提交。请求提交本身不必成为发布提交。

`cloud-release-followup` 会核对提交属于 main、两端版本/Android版本码一致、发布说明非空，拒绝覆盖正式发布或移动已有标签。创建标签前，必须等该完整SHA的 `quality` 和 `desktop-packaged` 全部成功。只接受 main 推送或显式候选检查；PR合并视图、旧提交和单纯的静态检查不能替代候选结果。检查失败立即停止，不创建标签；尚未执行或在途则最多等待110分钟，并给出对应运行链接。

主分支会提前运行全量workspace测试（Windows、macOS、Linux）、Android源码编译与宿主测试、静态/Runtime合同和按风险选择的桌面打包验证。平台矩阵不因单个平台失败而取消其他平台；新main提交也不取消已明确用于发布的候选检查。PR与dev仍按受影响包运行测试。完整候选检查比原先仅静态检查更耗时，换取在打标签之前暴露阻塞。

`desktop-packaged` 还会在一次性 Windows runner 上使用小型载荷编译生产 Inno 脚本，实际执行普通安装及七条数据迁移/保留流程。正式发布在后台更新验证之外，再使用真实交付的 EXE 重跑这些流程；任一失败都会阻断发布，日志随诊断资产保留。

候选通过后才创建新标签并显式调度原 `desktop-release` 稳定发布流水线。正式发布入口也复核同一SHA的候选结果；完整测试、构建、安装验证、Release与更新源验证继续执行，不跳过门禁。Android候选验证复用 `mobile.yml`，不另建一套Gradle命令。

如果创建标签后调度失败，可重跑该入口；相同标签只能指向相同提交，已有在途或成功运行不会重复启动。原发布流水线失败时先读确切日志：纯基础设施问题可按原能力重跑，源码修复则使用后续新补丁，不能移动旧标签。

请求默认停用。维护者可手动运行该工作流的 `dry_run=true`，仅核对请求目标，不创建标签或发布。此入口仅覆盖本轮1.3.x；切换版本系列前另行审查。
