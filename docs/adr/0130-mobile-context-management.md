# 手机端上下文管理的归属和非破坏性边界

## 背景

手机直接调用 API 与手机继续电脑会话使用不同的历史所有者。手机 API 会话此前逐条组装全部历史，长会话没有主动压缩入口。直接修改电脑会话的本地镜像无法改变电脑实际发送给模型的内容。

## 决策

- 手机 API 会话以 `MobileContextManager` 负责模型输入选择、估算与摘要。上下文起点、摘要和自动压缩开关进入现有会话元数据；旧记录缺省使用全部历史，手机备份随会话保存这些字段。
- 上下文起点按消息 ID 定位，先定位再筛选可发送内容。压缩仅在摘要完整成功后提交新起点，保留至少最近三轮并按用户回合切分；失败与生成期间取消不提交。
- 原始消息与图片不因压缩或重置而删除。占用估算明确标注；自动压缩默认开启，在已知模型容量、发送前估算达到约 80% 时执行。摘要请求不注册绘图工具，并在当前模型、分组中分批生成。
- 电脑会话只经 `session.context`、`session.context.compact`、`session.context.auto` 操作 Runtime 现有上下文控制，不引入第二套电脑压缩策略。自动开关为当前运行会话的覆盖值，重启恢复电脑配置。
- `session.context.cancel` 按请求 ID、操作类别和会话校验后传播到模型调用；连接停止时中止在途辅助操作。四项方法在 `session.list` 协商后才由手机发出，旧电脑不支持时显示升级说明。
- 远程“新上下文”通过同一电脑的新会话实现，保留旧电脑会话；不把清空手机镜像当作清空电脑上下文。

## 后果

手机与电脑的上下文仍各有唯一所有者。压缩会产生模型调用用量，摘要不能保证逐字保留细节，因此界面说明费用与完整历史保留方式。电脑占用可能尚无统计；手机估算受模型分词和图片处理方式影响，不冒充精确计费数据。

上下文起点同时保存消息 ID 与创建时间。重试删除起点时可按时间恢复边界；旧数据缺失起点且没有时间时，历史选择保守返回空集，但显式的新输入始终发送，避免重新带入已排除话题或发送空请求。该增量字段缺省为 null，兼容存量备份。
